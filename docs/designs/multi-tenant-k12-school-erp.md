# Design: Multi-Tenant K-12 School Management ERP

## Problem Statement

K-12 schools run their most sensitive operations — who is legally enrolled, who showed up today, who owes what — on paper registers, Excel files, and legacy SIS software that staff tolerate rather than use. A founder wants to replace that stack with a multi-tenant web platform where each school is a tenant, starting with the operational core schools touch every single day.

## Demand Evidence

**Thesis stage — none yet, and the design does not pretend otherwise.**
- No named school, no paying customer, no waitlist behavior.
- The founder's stated conviction: multi-tenant architecture, K-12 as the first vertical.
- Design implication: the plan optimizes for cheap tenant #1 onboarding and a wedge a real school can trial in days — because the first pilot is the experiment that decides everything.

## Status Quo

- **Paper admission & withdrawal register** — the legally expected source of truth in most jurisdictions.
- **Excel fee ledgers** — one workbook per clerk, no audit trail, arithmetic by hand.
- **WhatsApp groups** for parent communication.
- **Legacy SIS, if any** — bought by the trust, hated by the front office; data entry feels like punishment, so it is quietly abandoned.
- Cost of the status quo: fee-day chaos, unprovable attendance disputes, mid-year transfers done on a sticky note.

## Target User & Narrowest Wedge

- **Target user:** the owner/principal of a small-to-mid private K-12 school (hundreds, not thousands, of students) — the person who signs, pays, and suffers when fee day or an attendance dispute goes wrong.
- **Narrowest wedge (the paper-killer):**
  1. Admissions lite: inquiry → applicant → offer → enrolled (or no-show)
  2. Dated enrollment + section roster
  3. Daily attendance in under 15 seconds per section
  4. Fee collection: itemized heads, printed receipts with unique serials, end-of-day cash reconciliation
  5. Parent read-only view: attendance today, dues, receipts

## Constraints

- Multi-tenant from line one: shared schema, `tenant_id` on every row, enforced by Postgres RLS, proven by an adversarial cross-tenant test suite (forged IDs, direct query paths) — not by app-code filtering.
- One deployable monolith (API + responsive PWA). No microservices, no native apps.
- Jurisdiction-neutral kernel: rules stored as config (rule class, effective dates), never hardcoded law.
- Work offline-tolerant for attendance (cheap tablets in classrooms vary in connectivity).

## Premises (agreed by founder)

1. **Time is the product.** A student is a timeline of dated enrollments, not a row with a status. Fees are a ledger, not a balance field. Results and posted documents are append-only facts; corrections supersede, never overwrite.
2. **Person ≠ role.** One person, dated relationships. A teacher who is also a parent is one record with two roles. Guardians hold independent, dated rights (view, pay, pick up).
3. **Tenancy is a database guarantee**, enforced by RLS with an adversarial test suite from day one.
4. **Monolith-first.**
5. **The wedge is the paper-killer** (see Target User). Report cards, payroll, transport, timetables come after a pilot school signs.
6. **Jurisdiction-neutral core.** Rule classes: statute (cannot violate), standard, accounting practice, school policy (configurable), operational quality.

## Approaches Considered

- **A) Kernel-first, everything** — full temporal kernel before any screen. Most correct; months of invisible work with no design partner. **Rejected:** no feedback loop while burn continues.
- **B) Desk-first sprint** — visible modules on naive models (status enums, balance fields). Fastest demo. **Rejected:** this is precisely the data model that collapses at the first mid-year transfer and year-end rollover — the moments that decide whether a school buys.
- **C) Vertical wedge to kernel standard (CHOSEN)** — build only the wedge, but on the temporal kernel with RLS tenancy. Demoable in weeks, correct exactly where schools poke hardest.

## Recommended Approach (C, in brief)

**Kernel entities (append-only facts, no UPDATE of posted rows):**
```
Tenant
Person / Identity (effective-dated: legal name history, identifiers)
Relationship (person↔person, type, rights[], valid_from/to, court_order_id?)
Org / Campus
AcademicYear / CalendarDay (date, in_session, type)
Enrollment (student, campus, entry_date, entry_type, exit_date, exit_type,
            grade, calendar_id)                      -- close-and-open, never edited
SectionRoster (section, student, start_date, end_date)
AttendanceTaken (section, date, taken_by)            -- was the register even called?
AttendanceEvent (student, date, category, source)    -- denominator = in-session days ∩ enrollment window
Invoice (posted) → InvoiceLine
CreditNote / DebitNote (references invoice)
Receipt (unique serial, never reused) → Allocation (receipt, invoice_line, amount)
CashSession (float, expected, counted, variance reason)
```

**Wedge screens:** tenant onboarding wizard (school → year → calendar → grades → sections), admissions pipeline, 15-second attendance roster, fee desk (auto-allocation with manual override, receipt print, day-close), parent view.

**Non-goals until pilot signed:** timetable engine, exams/report cards, payroll, transport, comms (SMS/WhatsApp), payment gateway, ID cards, multi-campus consolidation.

**Acceptance tests (a module is done when these pass):**
- E1 mid-year section transfer preserves attendance on the owning section
- E2 mid-year grade change = close-and-open enrollment, no date overlap
- E8 re-admission = same person, new enrollment; old dues and documents intact
- F1 two cashiers paying the same partial amount produce the identical allocation split
- F9 bounced cheque keeps the original receipt serial; reversal is a new document
- F16 canceling a receipt after a later month is fully paid is refused (credit note instead)
- AT4 attendance cannot be marked on a non-session day; AT5 a student enrolled Wednesday is not "absent" Monday–Tuesday
- Y1 rollover runs on promotion decisions (flags), not on editing grade in place
- SEC1 adversarial suite: tenant A cannot read or write tenant B through any path, including forged IDs and direct SQL sessions (`SET ROLE authenticated` in tests)

## Open Questions

1. Which jurisdiction/pilot country for tenant #1? (Decides calendar conventions, receipt format, statutory documents.)
2. Payments: cash-first only, or gateway in v1? (Recommend cash-first: zero integration risk; gateway after pilot.)
3. Pricing: per-student/month, flat/month, per-campus? (Undecided — decide with tenant #1's willingness to pay.)
4. Parent comms channel for the wedge: none (read-only portal) vs WhatsApp deep-links?
5. Product name and brand.

## Success Criteria

- One named pilot school live with real students within 6 weeks of build start.
- All acceptance tests above green, including SEC1.
- Fee day runs end-to-end: collect → print receipt → day-close reconciles to zero variance.
- Mid-year transfer and year rollover performed on the pilot's real data without manual DB surgery.

## Distribution Plan

Web service (PWA). Deploy on managed infra (host + managed Postgres TBD — pick boring, cheap, one-region). CI via GitHub Actions: typecheck, tests (including the RLS adversarial suite), deploy on merge to main; preview env per PR for pilot feedback.

## Dependencies

- One pilot school (the assignment below).
- A decision on jurisdiction pack for calendar + receipt conventions.
- Nothing else blocks the wedge.

## The Assignment

**This week, before writing any code:** name one school. Get an introduction to its owner or principal and ask for one thing — to sit quietly during one admissions day and one fee-collection day and watch. Not a demo, not a pitch. If you cannot get that visit, you have a distribution problem before you have a product problem — and finding that out costs one week, not six months.
